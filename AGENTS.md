# Project rules

- Every business-rule number lives in `md_mpa_config` (the settings register) and is changed only through the `update_config_param` RPC (Supervisor only, mandatory reason, audited); never hard-code such values — one controlled, audited source keeps the product configurable per CFG-001.
- Client code reads numeric rules via `useConfigNumber(key)` (suspense query); keys live in `src/services/config/configNumber.ts` with no client fallbacks — a missing/unreadable value throws to the error boundary. Non-admin visibility is a per-key RLS allow-list on `md_mpa_config`; every setting carries a range or format enforced by a table trigger — the server is the single source of truth.
- Settings are snapshotted server-side (`config_snapshot`, overwritten on insert, frozen on update) on challenges, enrolments, assessment attempts, interview bookings and award decisions; rules for an existing record read its snapshot — later setting changes must not alter running work. Per-currency money thresholds live in `md_legal_review_thresholds` (keyed by `param_key`) and change via `update_config_param('money:<id>', …)`.
- SECURITY DEFINER functions are not executable by anon/authenticated unless the client calls them or an RLS policy needs them; trigger functions are never executable — keeps the exposed API minimal.

- Challenge `status` and `current_phase` change only inside server steps (complete_phase, award RPCs); a guard trigger refuses client writes and derives status from phase via `fn_status_for_phase` — one place enforces the ST-24 map and step owners.
- Award decisions go recommend → confirm (different person) or countersign (Senior Admin/Supervisor) through `recommend_award`/`confirm_award`/`return_award`/`countersign_award`; status sets and allowed moves live in `md_status_sets`/`md_status_transitions` — rules stay data-driven and auditable.
- Views in public use security_invoker=true; helpers that must bypass RLS for a view live in the non-exposed `private` schema — base-table RLS stays the single access gate.
- Creator governance selection is centralized in the creator service, and the form stays mounted during Draft mode changes so hidden fields and saved draft identity are preserved.
